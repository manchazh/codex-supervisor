# M2: единый Codex TUI и фоновое наблюдение лимитов

**Это интеграционный прототип.** Уже подтверждены реальные квоты из независимого read-only RPC-клиента и запуск самостоятельного watcher на машине пользователя. **Новая общая оболочка ещё требует ручной проверки.**

## Архитектура

Одна пользовательская команда/двойной клик запускает один Python управляющий процесс в штатном Windows PowerShell. Внутри этого процесса:

1. Проверяется папка проекта и наличие Codex CLI.
2. Берётся эксклюзивная OS-блокировка хранилища монитора.
3. Создаётся фоновый поток read-only quota watcher.
4. В текущей консоли (с наследованием stdin/stdout/stderr) открывается **обычный Codex TUI**, явно подключённый к уже работающему shared daemon через `--remote unix://`.
5. После **штатного выхода** из управляемого Codex процесс прекращает watcher, дожидается завершения запроса квот, освобождает блокировку. **Не трогает другие TUI и общий app-server**.

Код транспорта использует только RPC `initialize`, `initialized`, `account/rateLimits/read`. Запуск TUI **не посылает модельный промпт**. После запуска любые обычные действия пользователя в Codex могут расходовать лимиты как раньше.

Первичная цель — **объединённый запуск и остановка**. Автоматическое продолжение незавершённой работы после исчерпания и восстановления лимита пока **НЕ реализовано**.

## Как проверить без запуска Codex

В отдельном тестовом клоне ветки `issue/16-integrated-launcher`, из корня:

```powershell
python -m launcher --project "D:\arbeiten\codex-supervisor-integration" --new --dry-run
```

Dry-run не создаёт процессов, не выполняет RPC и не вызывает модель. Он печатает путь, режим и флаги будущего запуска.

## Ручной запуск (ТОЛЬКО после согласования)

Потребуется Python 3.11+, локальный Codex CLI, уже работающий общий app-server daemon (`codex app-server daemon version` показывает `running`). В отдельном тестовом клоне:

```powershell
python -m launcher --project "D:\arbeiten\codex-supervisor-integration" --new --interval 300
```

Или двойной щелчок по `start-codex-supervisor.cmd` — откроется **отдельный Windows PowerShell**, меню «новая/последняя/отмена». По умолчанию папка проекта — папка самого CMD. Для другого проекта:

```powershell
.\start-codex-supervisor.cmd "D:\arbeiten\some-other-project"
```

**Поставка прототипа пока не одnofайловая**: рядом с CMD должны быть пакеты `launcher/` и `quota_probe/` из этой ветки, плюс Python 3.11+ на ПК. Это сознательное ограничение M2; собственный портативный релиз для ПК без Python нужно собрать отдельно и проверить на чистой Windows. Архив `Codex Launcher 0.1.0` / тег `codex-launcher-v0.1.0` не меняются.

Открывая тестовый Codex, **не отправляйте модельных промптов для smoke-теста**. Для выхода используйте штатную команду `/quit` внутри TUI. Затем убедитесь, что оболочка PowerShell вернулась и фоновый watcher завершился. Все другие сессии Codex должны продолжать работать.

## Если ранее запущен самостоятельный watcher

Текущий `quota_probe.watch_cli` использует то же локальное хранилище и ту же OS-блокировку. Пока он активен, **новый объединённый Launcher не запустится** и прямо сообщит о конфликте. Он не будет завершать старый watcher или создавать второй. Если нужно проверить новый вариант, сначала **самостоятельно** завершите свой отдельный тестовый watcher через Ctrl+C в его PowerShell. Чужие Codex-сессии не закрывать.

## Журнал и секреты

Только агрегированные проценты квот, окно и reset — локально:

```text
%LOCALAPPDATA%\CodexSupervisor\quota\managed-watch.log
%LOCALAPPDATA%\CodexSupervisor\quota\last-seen.json
```

Ни account ID, ни email, ни thread UUID, ни переписка в логи не попадают. Ограничение: при сбоях app-server чтение лимитов повторяется с backoff; монитор может временно не иметь свежего снимка, но **никаких модельных действий от этого не происходит**.

## Ограничения / риски

- **Не интегрирует управление конкретным thread**. Команда `resume --last` по выбранной папке соответствует проверенному UX архивного Launcher, но не гарантирует корректность автоматического восстановления. Точный ID и состояние задачи — отдельная Issue.
- Монитор здесь работает в потоке, а не Windows Service: если процесс Python аварийно завершится, watcher остановится. Вне активного ПК никакого слежения нет.
- При очень долгом/зависшем служебном RPC закрытие оболочки может занять до 20 секунд. Завершаются только свои дочерние proxy, основной daemon не затрагивается.
- Встроенное нормальное завершение проверять через `/quit`; обработку повторного Ctrl+C в разных консольных хостах ещё предстоит проверить отдельно, не симулируя на рабочих сессиях.
- Одна активная подписка/один контекст лимитов на OS-профиль; монитор не различает квоты разных одновременно авторизованных учётных записей и не управляет чужими TUI.
- `--remote unix://` намеренно **не откатывается на embedded**. Если на другом ПК shared daemon не запущен, сначала нужно настроить поддержку, а не тихо продолжать без наблюдателя. Никакого auto-start/restart daemon.

## Unit tests (без модели и сети)

```powershell
python -m unittest discover -s tests -p "test_*.py" -v
```

Тесты проверяют аргументы и cwd CLI, старт и остановку mock watcher, отказ при дубликате, лог/запрет секретов, Ctrl+C/ошибки, CRLF batch и совместимость Windows/Linux.

После этой интеграции следующий этап — **контроль конкретной сессии и недоделанного задания** и только потом автопродолжение при подтверждённом доступе.
