# Codex Supervisor — хэндоф для нового чата

**Дата передачи:** 15 октября 2026 года.  
**Репозиторий:** https://github.com/manchazh/codex-supervisor  
**Статус:** работа над Supervisor **приостановлена по решению пользователя**. В исходном чате продолжается основная задача — сайт Аверса. Этот хэндоф предназначен для **нового отдельного чата**, который будет заниматься исключительно Codex Supervisor.

> **Важно:** хэндоф не означает завершённость продукта. Есть работающие части, но безопасного автоматического продолжения незавершённого задания после восстановления лимитов **ещё нет**.

## 1. Что хочет пользователь

Нужна **одна универсальная утилита**, запускающая привычный **Codex CLI TUI в Windows PowerShell** в произвольной папке проекта и **незаметно** включающая наблюдение за реальными лимитами Codex. Конечная цель — при достижении лимита корректно ждать восстановления и затем **автоматически возобновить именно ту незавершённую задачу**, без дублирования ходов и вмешательства в посторонние открытые сессии.

- Никакого отдельного обязательного GUI/Tkinter и отдельного пользовательского «ночного режима». Пользователь хочет работать через привычный PowerShell и запускать **одну** утилиту.
- Ранее созданный **переносимый Codex Launcher 0.1.0** должен служить основой привычного UX (двойной щелчок, новая или последняя сессия, произвольная папка). Его **архив и тег неизменны**. Итоговый релиз должен обходиться без отдельной установки Python на Windows; в нынешнем интеграционном прототипе Python ещё требуется.
- Реальный Codex и авторизация устанавливаются на каждом ПК отдельно; перенос аккаунта и приватных сессий между ПК не обещать.
- Диагностика **не расходует модельные токены**: без тестовых «продолжай», `turn/start` и иных модельных ходов без явного разрешения.
- Категорически не останавливать/restart существующий `app-server daemon`, не закрывать посторонние Codex TUI, не менять глобальную конфигурацию Codex, Windows ACL, sandbox, approval policy, PowerShell ExecutionPolicy; не предлагать опасные bypass-флаги.
- Общаться **кратко, по-русски**, давать **одну конкретную PowerShell-команду за шаг** и ждать вывода. Никаких автоматических merge PR без явного согласия владельца.

## 3. Что реально работает / подтверждено

**A. Архивный Launcher 0.1.0.** Ранее пользователь проверил обычный запуск Codex и продолжение последней сессии на Windows. Windows-вариант `start-codex.cmd` не требует Python, открывает PowerShell, подхватывает каталог размещения, позволяет новую сессию или `codex resume --last`. Изолированная версия сохранена отдельным ZIP/тегом. Она сама не умеет читать лимиты и не возобновляет зависшие задания автоматически.

**B. Реальное чтение квот без модели.** На Windows с **Codex CLI/app-server daemon 0.162.1** `python -m quota_probe` установил независимое соединение через `codex app-server proxy`, провёл настоящий **RFC6455 WebSocket handshake** и отправил только `initialize`, `initialized`, `account/rateLimits/read`. Вернул два окна — 300 минут и 10080 минут — с used %, resetsAt. Модельных сообщений не было. Ранний таймаут был вызван ошибочным допущением, что proxy принимает JSONL; исправление WebSocket уже работает. Исторические проценты квот **не являются текущими показателями**.

**C. Отдельный M1 watcher.** Пользователь запустил `python -m quota_probe.watch_cli --interval 60`, получил первый реальный снимок обоих окон; позже **штатно остановил этот самостоятельный монитор Ctrl+C и закрыл его окно**. Долговременная работа с реальными переходами квот, reconnect и reset в боевой среде пока не доказана. По умолчанию watcher опрашивает раз в 5 минут, с увеличивающимися задержками при ошибках. Он не посылает модельные ходы.

**D. Совмещённый M2 прототип.** `python -m launcher --project <тестовый-проект> --new --dry-run` на ПК пользователя корректно показал планируемые параметры — без модели и RPC. Первый живой запуск `python -m launcher --project <тестовый-проект> --new --interval 60` **открыл штатный Codex TUI и напечатал сообщение о запуске watcher**. Однако обнаружился критический дефект: UI показывал **каталог daemon** (`~\\.codex\\app-server-daemon\\workdir`), а не выбранный проект. Не отправляли модельных промптов. Этот недостаток исправлен в PR #17 введением явного `--cd <канонический путь проекта>` для новых и resumed remote-сеансов. После фикса были зелёные офлайн-тесты, но **повторного живого скриншота с правильной папкой ещё не было**.

**E. Завершение первой M2 сессии.** После команды `/quit` CLI показал сообщение об **отключении от server task**, с формулировкой `Any running work continues`, и PowerShell снова стал доступен; служебные сообщения watcher в консоли были видны нестрого в ожидаемом порядке. **Не доказано** по одному скриншоту, что серверный task полностью завершён, что не осталось зависшего процесса и что watcher аккуратно отпустил все ресурсы. Ничего не завершать принудительно и не запускать второй модельный turn ради проверки.

**F. CI.** На коммите **`19a0dcc90804538924a1346597b8ae824c37e1e4`** все три GitHub Actions workflows (M2 интеграция, RPC, watcher) завершились **success на Windows и Ubuntu**. Это **офлайн-тесты с фальшивыми процессами/сервером**, не proof боевой безопасности resume.

## 4. Текущие ограничения и открытые риски

1. **Нет автопродолжения**. Ни наблюдение процента, ни достижение времени `resetsAt` не доказывает, что модельному клиенту можно отправить новый ход. Нет привязки конкретной незавершённой задачи, строгих статусных событий `turn/completed`, `usageLimitExceeded`, проверки approvals и гарантии отсутствия параллельного turn.
2. **Live-фикс `--cd` не проверен** после обновления клона до `19a0dcc`. Прежний TUI мог открывать не тот проект — **не выполнять в нём никакой файловой задачи до ретеста**.
3. **Состояние server task** после первого `/quit` неизвестно; не путать «отключились от задачи» с «задача завершена». Не угадать и не повторно отправить сообщение.
4. **Жизненный цикл watcher** в объединённом процессе полностью не подтверждён: поток должен прекращаться после штатного выхода из управляемой TUI. Состояние после Ctrl+C / ошибок / закрытия консоли / повторного запуска — проверить аккуратно.
5. **Портативная поставка M2 пока требует Python 3.11+**. На Windows финальный пользовательский вариант должен обходиться без его ручной установки, сохраняя привычный double-click. В архиве 0.1.0 Windows-батник самодостаточен, но ещё без Supervisor.
6. **Не полноценный 24/7 сервис**: watcher работает, пока запущен пользовательский управляющий процесс и ПК. Долговременное наблюдение, restart after crash, предотвращение повторных запусков после рестарта — отдельные технические задачи.
7. Одна блокировка на локальное состояние квот; при активном самостоятельном watcher объединённая версия отказывает в запуске — **не убивает чужой watcher**, что правильно для безопасности, но UX нужно позже спроектировать.
8. Текущая реализация делает отдельное короткое read-only WebSocket-подключение при каждом опросе, не использует долгоживущее event subscription. Возможность сервера выдавать нужные статусные события требует отдельной проверки.
9. Конкурентные TUI, sandbox Windows и lock/workspace permissions могут создавать риски; не «чинить» их повышением прав или завершением чужих процессов.

## 5. Следующая безопасная последовательность после возврата к проекту

**Не выполнять сейчас.** Это маршрут для следующего чата; давать пользователю **одну команду за раз**, после согласования.

1. Проверить актуальный head PR #17 / ветки и локальной копии пользователя. Никаких merge/rebase/force push. Первым действием будущего теста рекомендуется **только dry-run** с новой командой, чтобы увидеть наличие `--cd` и правильного каталога без запуска модели. Пример для будущего чата:
   ```powershell
   cd "D:\arbeiten\codex-supervisor-integration"; python -m launcher --project "D:\arbeiten\codex-supervisor-integration" --new --dry-run
   ```
2. Если пользователь разрешит живой smoke, осторожно запустить **новый тестовый TUI без промпта** и проверить, что status/cwd соответствует тестовой директории. Учесть неизвестное состояние ранее отсоединённой server task. Никаких действий в рабочем проекте Аверса только ради теста Supervisor.
3. Штатно завершить только **управляемый тестовый** TUI. Подтвердить на уровне логов/блокировки остановку watcher, отсутствие собственного proxy и сохранность работающего daemon и других TUI.
4. Исправить выявленные локальным smoke проблемы; оставить офлайн Windows/Linux регрессионные тесты. Не спешить с упаковкой, пока управление процессами не надёжно.
5. Продумать и реализовать portable Windows релиз **единого приложения**: single launch entry-point, без отдельной установки Python (способ упаковки выбирается после оценки объёма и SmartScreen), с опциональным `--project` и `resume`. Сохранить оригинальный архив 0.1.0.
6. **Отдельным техническим этапом** исследовать точный серверный thread/task lifecycle, квотный отказ и доступность после восстановления; сделать имитационные тесты idempotency, stop, approvals, crash, unknown outcome. Реальное автоматическое продолжение только после строгой привязки к конкретной незавершённой задаче, защиты от дублирования и явного согласования проверки.
7. Публиковать изменения только через ветку/PR, документировать фактические доказательства, **не выдавать «монитор готов» за «Supervisor умеет безопасно продолжать задачу»**.
