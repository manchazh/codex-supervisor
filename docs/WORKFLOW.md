# Принципы работы ChatGPT + Codex + GitHub

**Цель:** использовать ChatGPT как постановщика задачи, консультанта и независимого ревьюера, Codex как исполнителя в рабочей папке, GitHub как проверяемый источник договорённостей и изменений. Это **рекомендуемый процесс**, а не автоматическая встроенная связь между двумя продуктами.

## Роли и границы

| Участник | Отвечает за | Не предполагается автоматически |
| --- | --- | --- |
| Пользователь | Приоритеты, выбор решений, согласование рисков, приёмку и merge | Не обязан писать терминальные команды |
| ChatGPT | Анализ требований, небольшие Issue, сверка PR с ТЗ, обнаружение пробелов, вопросы пользователю | Не видит локальные файлы и не запускает Codex без подходящего доступа |
| Codex | Чтение проекта, реализацию конкретной Issue, тесты, журнал, ветку и PR | Не выбирает за пользователя следующую задачу, не утверждает результат |
| GitHub | Текст задач, обсуждение, файлы веток, diff, история ревью и merge | Не делает результаты автоматически корректными |

Один вопрос пользователя — **один следующий понятный шаг**. Автоматизация полезна лишь там, где проверена и не нарушает разделение полномочий.

## Цикл задачи

1. **Сформулировать цель.** Что меняем, зачем, что не трогаем. Вынести критерии приёмки и ограничения.
2. **Создать GitHub Issue.** Одна небольшая проверяемая единица работы, а не сразу весь долгосрочный план. Дополнения фиксировать в Issue, а не только в истории чата.
3. **Codex готовит среду.** Читает `AGENTS.md`, `README.md`, журнал решений и контекст задачи. Сверяет `git status`, текущую ветку и origin. При конфликте или чужих незакоммиченных правках **останавливается**, а не делает reset/clean.
4. **Работа в отдельной ветке.** Codex реализует одну Issue, делает подходящие проверки, записывает ограничения и оформляет PR с осмысленным русским описанием. Не пушит напрямую в `main`, не сливает PR без разрешения.
5. **Независимое ревью.** ChatGPT читает **реальный diff** через GitHub, проверяет логику, безопасность, тесты, пользовательские сценарии. Слова «всё готово» и число тестов — не замена осмотра кода.
6. **Приёмка пользователем.** Проверить ключевой сценарий в настоящем UI/CLI, если автоматические тесты его не покрывают.
7. **Merge и следующая задача.** Только после явного разрешения пользователя. Закрыть Issue и обновить краткий журнал передачи контекста; не запускать следующую автоматически.

### Шаблон Issue

```markdown
## Цель
Что должно измениться и для кого.

## Контекст
Ссылки на актуальные документы, существующее поведение, ограничения.

## Область изменений
Что разрешено менять; что категорически не трогать.

## Задачи
Конкретный небольшой объём работы.

## Критерии приёмки
- [ ] Основной сценарий проверен.
- [ ] Есть подходящие автоматические тесты.
- [ ] Побочные эффекты и ограничения объяснены.
- [ ] Нет изменений в production/секретах без разрешения.

## После выполнения
PR на ревью; без автоматического merge.
```

### Пример поручения Codex

> Работаешь в проекте PROJECT. Выполни только GitHub Issue №N: URL. Проверь текущие `git status`, ветку и правила `AGENTS.md`. Используй отдельную ветку от свежей основы без удаления чужих изменений. Реализуй критерии, запусти подходящие тесты, подготовь PR и объясни непроверенное. Не сливай PR, не меняй production и разрешения, остановись после этой задачи.

Это **текст задания**. Он не даёт Codex технических разрешений, которых у него нет.

### Пример запроса ревью к ChatGPT

> Проверь PR URL против Issue URL. Прочитай реальный diff и критичные затронутые файлы. Найди потенциальные ошибки, нарушения безопасности, недостающие тесты и несоответствия требованиям. Отдельно покажи, какие утверждения Codex проверены, а какие основаны только на его отчёте. Ничего не сливай без моего разрешения.

## История проекта и продолжение

Поскольку контекст модели ограничен и сессии могут меняться, храните **краткие проверяемые артефакты в Git**, а не только в чате:

- `AGENTS.md` — постоянные правила проекта.
- `docs/DECISIONS.md` — решения с датой, причинами и последствиями (не выдавать гипотезы за факты).
- `docs/HANDOFF.md` — текущая ветка, задача, что проверено, что осталось, что нельзя запускать.
- Issue/PR — фактическая история задач и кода.

`HANDOFF` не должен включать токены, закрытую переписку, лишние персональные данные и секретные пути. Старые записи сохраняйте как историю, новые — добавляйте сверху. Если сессия перезапущена, нужно проверить контекст **до новой записи**, особенно при выборе `resume`.

Не считайте просмотр старой переписки доказательством того, что можно безопасно повторить незавершённое действие. На GitHub внешняя операция могла выполниться до сбоя ответа. Прежде чем делать повтор, проверьте фактическое состояние.

## Работа с решениями и утверждениями

Отделяйте:
- **Факт:** проверено командой, diff, файлом, тестом или пользователем.
- **Отчёт исполнителя:** Codex утверждает, что тест прошёл, но ревьюер его не запускал.
- **Гипотеза:** предполагаемая причина или решение, не подтверждённое экспериментом.
- **Согласованное решение:** явное «разрешаю» пользователя.
- **Ограничение:** непроверенная возможность, неполный эксперимент, ошибка окружения.

При ревью не превращайте «не проверяли» в «не работает», а «указано в help» — в «проверено в реальной задаче».

## Контроль изменений и безопасности

- **По умолчанию:** узкий scope работы, `workspace-write` / `on-request`, ручные approvals для требующих их действий.
- **Только после согласия:** merge, публичная публикация новых данных, production/deploy, токены, изменение системных прав, обновление CLI, принудительная остановка процессов, изменение модели/аккаунта, открытие сетевых портов.
- **Никогда автоматически:** удаление незакоммиченных изменений, широкие allow-правила на незнакомые команды, бесконечные retry, обход квот, подтверждение опасных запросов за человека.
- Разрешение на выполнение **задачи** не означает разрешение на любое системное действие.
- Сбой sandbox требует диагностики, а не `danger-full-access` как безусловного решения.
- При нескольких Codex-сеансах проверять фактическую ветку и состояние рабочей папки; параллельную запись в один workspace предотвращать.

## Как согласовывать коммуникацию

**Для пользователя:** один шаг за раз, короткие инструкции и скриншоты при необходимости. Не заставляйте копировать большие одноразовые PowerShell-блоки без причины.

**Для задач, PR и журналов:** писать на согласованном языке проекта. Здесь принят русский язык (технические идентификаторы/код могут быть английскими). Каждое сообщение о ходе работы содержит проверяемый результат, а не «идёт процесс».

**Для публичного репозитория:** инструкция должна быть воспроизводима **на чужом компьютере**. Нельзя подменять параметры шаблона чьими-то рабочими путями, конфиденциальным `origin` или конкретной подпиской.

## Если ревью нашло ошибку

Не открывайте новую задачу/PR для каждой мелкой правки. Попросите Codex **продолжить ту же ветку и исправить замечание в текущем PR**. После изменения head SHA проверьте diff заново, повторите минимальный пользовательский тест и только затем решайте вопрос о merge.
