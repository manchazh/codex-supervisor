# Архитектура Supervisor: проверяемые решения

**Этот документ задаёт требования к реализации, а не утверждает, что код готов.** Спецификация протоколов Codex меняется; всё ниже следует проверять в реальной установленной версии.

## Слои приложения

```text
┌─────────────────────────────────────────────┐
│ Единый интерфейс: чат, история, Стоп/Пауза  │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│ Supervisor: machine state / checkpoint      │
│ audit trail / session lock / permission gate│
└─────────────┬─────────────────┬─────────────┘
              │                 │
┌─────────────▼────────────┐ ┌──▼─────────────┐
│ Транспорт Codex          │ │ Хранилище     │
│ app-server RPC           │ │ метаданных    │
└─────────────┬────────────┘ └────────────────┘
              │
┌─────────────▼────────────┐
│ Локальный Codex          │
│ подтверждённый API       │
└──────────────────────────┘
```

Предпочтительный транспорт для прототипа — локальный stdio. При выборе WebSocket ограничить адрес `localhost`, подтвердить аутентификацию и способ остановки. Не передавать управление открытым чужим TUI через GUI-клики или отправку клавиш.

## Данные и идентичность

Хранить **минимальные** метаданные, например:

```json
{
  "schema_version": 1,
  "project_id": "локальный-неперсональный-id",
  "repo": "пример: owner/repository",
  "branch": "feature/one-issue",
  "thread_id": "uuid-пример-не-настоящий",
  "task_id": "issue-номер-или-внутренняя-задача",
  "turn_id": null,
  "status": "await_user",
  "auto_continue_enabled": false,
  "last_confirmed_checkpoint": null
}
```

Реальный cwd — локальная настройка, **не публикуется**. Сверять: canonical path, Git origin, ветку, account ID, thread ID, ID активного хода, наличие ожидающих approvals, последний подтверждённый результат внешних операций. Один lock на редактируемый workspace; PID сам по себе недостаточен для надёжного lock.

Состояние писать атомарно; после краша не считать, что прерванный ход не имел побочных эффектов. При неизвестном результате — `needs_review`.

## Квота

Сигнал `usageLimitExceeded` и `rateLimitExceeded` различаются; обычный HTTP 429 не даёт права отправлять повторный ход. Из доступных схем исследованного протокола известны: `ordinaryUsageAllowed`, `resetsAt`, `accountId`, но **их реальная работа в нужном сценарии ещё не проверена**.

Алгоритм будущей версии:

1. Получить подтверждённое событие квоты для **конкретного аккаунта и окна**; если Codex заявил `willRetry=true`, не добавлять внешний retry.
2. Сохранить checkpoint и ожидать до действительного `resetsAt` плюс защитный запас. Если `resetsAt` отсутствует или смешаны недельная/краткая квоты — остановиться для человека.
3. Проверить свежий ответ доступности **`ordinaryUsageAllowed === true`**. По часам ПК доступность **не угадывать**.
4. Убедиться в отсутствии уже продолжающегося turn, дубля события, завершённой задачи, чужой ветки и незавершённой внешней операции.
5. Допустить **не более одной** контролируемой попытки (на первом этапе), записав идентификатор до отправки. При неизвестном исходе не повторять.

Покупка кредитов, смена модели/аккаунта и обход ограничений не предусмотрены.

## Стейты

`idle` → `running` → `completed`;
`running` → `await_user` при вопросе/approval;
`running` → `await_quota` только при валидной квоте;
`await_quota` → `resuming` при свежем разрешении и сверке;
`running|await_quota|resuming` → `paused|stopped|needs_review` при вмешательстве, сбое или неясности.

У пользовательского стопа абсолютный приоритет; даже если таймер уже наступил, отправка нового turn запрещена.

## Контракты интерфейса

- Отображать отдельно сообщения пользователя, текст агента, события инструментов, предупреждения и решения безопасности.
- Историю брать из поддерживаемого Codex API, не дублировать приватные тексты в логах.
- Рендеринг и ввод не должны зависеть от часа суток или режима «ночь».
- Долгие поручения требуют описанной цели, контрольной точки и завершения.
- Не путать **открытую TUI-историю** с **правом на внешний turn**.
- Кнопки Стоп и Пауза имеют видимое подтверждение backend-состояния; не обещать мгновенную остановку внешней команды без доказательства.

## Тестовая матрица

1. Обычный вопрос завершён → нет auto-turn.
2. Подтверждённая квота, валидный reset и серверное разрешение → максимум один повтор.
3. 429 без признака квоты; stale reset; `ordinaryUsageAllowed=null`; `willRetry=true` → нет повторного turn.
4. Два проекта и два thread → отсутствие пересечения данных и команды.
5. Пользовательский Стоп перед/во время восстановления → ни одного следующего turn.
6. Краш на границе отправки; утрата ack; повторное событие; зависший процесс → `needs_review`, нет дублей.
7. Approval/вопрос → ожидает пользователя, не отвечает самостоятельно.
8. Нет сети, отказ входа, несоответствие аккаунта, чужая ветка → стоп.
9. Повторный запуск UI → истории и метаданные согласованы, неизвестное состояние помечено.
10. Windows sandbox неисправен → отказ от автоматического режима, не переход на `danger-full-access`.

Каждая симуляция использует фиктивный backend и виртуальное время; настоящие запросы модели требуют отдельно согласованного бюджета, сценария и способа остановки.

## Интеграция с GitHub и ChatGPT

Supervisor не должен требовать подключения ChatGPT для обычной работы с Codex: полезна опциональная связка. ChatGPT может формулировать Issue и проверять PR **через имеющиеся у него права GitHub**, но не принимает approve от имени пользователя. Следы решений — Issue/PR, а не приватный transcript.

## Не переносить в универсальное ядро

Жёсткие пути чужих ПК; секреты из `~/.codex`; прямую привязку к одному репозиторию; полноэкранные TUI-хуки без протокола; анализ содержимого пользовательского чата ради определения лимита; глобальные автозапуски без opt-in.
