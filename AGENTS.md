# Правила работы агентов в codex-supervisor

Этот файл — обязательный контракт для **исполнителя кода** (Codex или другого агента), работающего в этом репозитории. Внешний ChatGPT может выступать постановщиком/ревьюером, но не считается локальным агентом без фактического доступа.

## До работы

1. Прочитай `README.md`, `docs/PRODUCT.md`, `docs/ARCHITECTURE.md`, `docs/WORKFLOW.md`; для конкретной задачи прочитай полную GitHub Issue и актуальные комментарии.
2. Выполни неразрушающую проверку `git status`, ветки, `origin`, текущих изменений и наличия других активных сессий.
3. Если в workspace чужие незакоммиченные изменения, конфликт, неизвестная ветка, незавершённый merge или недостоверный источник задачи — **остановись, спроси**. Не делай `reset`, `clean`, `checkout` с потерей данных.
4. Работай **только над одной Issue** в отдельной ветке. В случае обновления текущего PR — продолжай существующую ветку, не создавай новый PR без нужды.

## Граница полномочий

- Не удаляй и не публикуй пользовательские файлы, секреты или истории чатов.
- Не обновляй CLI, не меняй sandbox/approval, профиль PowerShell, системные ACL, PATH, автозагрузку, службы, правила Firewall/Defender без отдельного явного согласия.
- Не разрешай собственные approvals, не используй `--yolo`, `danger-full-access` или `never` ради удобства.
- Не делай push в `main`, auto-merge, force push, production/deploy или массовые фоновые модельные вызовы.
- Для платных live-тестов, сетевых сервисов и влияющих на аккаунт действий сначала предложи точный сценарий, бюджет и остановку; дождись отдельного разрешения.
- **Публичный репозиторий:** исключи локальные абсолютные пути пользователя, реальные thread IDs, auth/cookies, реальные клиентские данные и личные чаты. В тестах используй фиктивные значения.

## Стандарты реализации

- Предпочитай небольшой работающий вертикальный срез вместо большой теоретической архитектуры.
- Отдельно проверяй UI, протокол и безопасность; мок-тест **не равен** реальному испытанию Codex.
- Обязательны тесты на ошибку, отказ, повторную доставку, остановку и восстановление состояния, где применимо.
- Текущий подтверждённый контракт версии CLI фиксируй тестами; не полагайся на вечность экспериментального app-server API.
- Разделяй управление новым Supervisor и чужими уже работающими CLI-процессами; **не переподключайся** к неизвестным сессиям.
- Никаких бесконечных повторов и «продолжай» без подтверждения незавершённой задачи и восстановленного лимита.
- Все объяснения, UX, PR, Issue, журналы, решения и коммиты пишутся **по-русски**; код/имена протоколов могут быть английскими.
- Документацию для посторонних пользователей пиши без предположений о локальных путях, конкретной ОС кроме явно заявленной поддержки или наличии GitHub CLI.

## Завершение задачи

1. Проверить фактический diff, пройти релевантные тесты и чётко указать, что **не проверено**.
2. Обновить в отдельном PR относящиеся к работе документы/журнал, если они предусмотрены.
3. Создать PR в `main` с русским описанием, ссылкой на Issue, тестами и рисками.
4. **Остановиться**, передать ссылку ревьюеру. Слияние и следующая Issue — только по решению пользователя.
